PRODUCT NORTH STAR — GAMIFIED TENNIS PROGRESSION (READ FIRST; see CLAUDE.md ★ section)
-------------------------------------------------------------------------------------
- tennisnow is a GAMIFICATION-FIRST tennis improvement app. The whole app is built so that logging
  real tennis makes your "game" level up. NOT a stats tracker, NOT a notes app: "Log your tennis ->
  watch your game level up." This is the spine — every feature must feed the Player Profile /
  progression / motivation loop, or it probably doesn't belong.
- THE PLAYER PROFILE is the centrepiece: real tennis SKILLS that grow like an RPG character, but every
  point is EARNED by real play. Visualised as a radar/level/XP profile.
- TENNIS SKILL MODEL (canonical taxonomy — reuse these names; extend deliberately + update CLAUDE.md):
  * Strokes: Serve(Aufschlag), Return, Forehand(Vorhand), Backhand(Rückhand), Volley, Smash, Slice,
    Lob, Drop shot.
  * Shot qualities: Power, Spin, Placement/Accuracy, Consistency.
  * Physical: Endurance(Ausdauer), Speed/Footwork, Agility, Strength.
  * Mental: Focus, Composure, Confidence, Tactics/Court IQ.
  * Match craft: serve games, break points, tiebreaks, clutch (derived from match data over time).
  * Equipment synergy: racket + stringing (tension kg, string, freshness) vs performance.
  Model it as a PURE-domain catalog in shared/domain (like BadgeCatalog): Skill{id,name,category} +
  SkillCategory enum + recency-weighted SkillRating. Flutter-free; icons/labels in presentation.
- PROGRESSION SYSTEMS: XP + Player Level(+title); recency-weighted skill ratings; streaks (built);
  badges (built; expand to skill-based); optional quests/challenges; the Player Profile/radar.
- GAMIFICATION GUARDRAILS (this is how we avoid the classic failure): logging stays sacred & fast
  (skill capture is OPTIONAL, never blocks Save); EARNED & HONEST (no fake dopamine, no inflated
  numbers, no pay-to-win, no streak-shaming); real tennis semantics (credible to a club player);
  meaningful not noisy (occasional, tasteful celebration; NO spammy notifications); the human/mental
  side is first-class.
- DERIVE, DON'T STORE, where feasible: compute progression from sessions; persist only what can't be
  re-derived (explicit skill self-ratings, unlocked-badge timestamps).
- COMMUNITY IS THE PLANNED DIRECTION (future, architect now — do NOT build yet): leaderboards, friends,
  head-to-head challenges, shareable Player Cards, clubs/ladders, seasons. COMMUNITY-READY INVARIANT:
  scoring is PURE + DETERMINISTIC (server could recompute/verify), stable client UUIDs, a clean future
  owner/userId seam, no "exactly one local player" assumptions, sharing is opt-in & granular.


CRITICAL ARCHITECTURAL DECISIONS (the "why", so they're never re-litigated blindly)
-----------------------------------------------------------------------------------
- LOCAL-FIRST, SYNC-READY. v1 stores everything on-device (no login, offline, private, cheap,
  zero logging friction). Chosen because logging friction is the #1 product risk and cloud adds
  none of the core value yet. The schema is sync-ready (see invariant below) so cloud accounts +
  multi-device sync can be ADDED later without a rewrite. Do not add a backend prematurely.
  >>> SUPERSEDED / EXTENDED (2026): the cloud pivot is now GREENLIT — see the section
  "CLOUD PIVOT: SUPABASE BACKEND + AUTH + TIERS" near the end of this file. Local-first stays as the
  OFFLINE-FIRST CACHE layer; Supabase becomes the source of truth for signed-in Pro users. Offline-first
  is NOT abandoned — it is preserved (the core loop must still work with no network).
- PLANNED BACKEND = SUPABASE — NOW BEING BUILT (was "future, NOT built yet"; greenlit 2026). The
  database syncs with Supabase (Postgres + auth + row-level security). The forward-design we kept paying
  for now pays off: persistence stays behind repository INTERFACES (a SupabaseXRepository / a sync layer
  drops in next to the DriftXRepository); the id/createdAt/updatedAt/soft-delete invariant on every
  entity maps 1:1 to Postgres rows; all scoring stays PURE + DETERMINISTIC so a Supabase edge function
  can recompute/verify XP/levels/skills/quests; the `userId`/owner seam (RLS keys on it) gets filled in.
  Full plan: see "CLOUD PIVOT: SUPABASE BACKEND + AUTH + TIERS" at the end of this file.
- BRAND MARK = CODED VECTOR (design_system/widgets/app_logo.dart): AppLogoMark (tennis-ball CustomPainter,
  court-green tile + optic-yellow ball + dark-green seam) + AppLogo (mark + "tennisnow" wordmark, "now" in
  brand green). No raster asset on purpose — scales crisply, theme-aware, §5 single-source-of-truth. Used
  on onboarding (first impression). Reuse this, don't drop in PNG logos.
- AI IMAGE ASSETS (Replicate etc.): the on-web session NETWORK POLICY blocks api.replicate.com
  (x-deny-reason: host_not_allowed). So Claude CANNOT generate/download images from here unless the
  environment is created with a policy that allowlists api.replicate.com + replicate.delivery, with the
  token as an env-var/secret (never in chat/repo). Otherwise the path is: user generates externally, we
  integrate the files. Premium guidance: AI raster is OK for logo / onboarding+empty-state illustrations;
  NOT for buttons/UI chrome (stay coded Flutter) or animations (use Lottie/Rive or coded TweenAnimation).
- FLUTTER + DART, single codebase. Chosen for store-ready iOS+Android, app-like performance,
  and strong charts/animation ecosystem (trends + motivation are visual). Avoids 2x native cost.
- RIVERPOD for state, GO_ROUTER for navigation, DRIFT/SQLite for persistence. Drift over a
  key-value store because trends/analytics need real relational queries done in SQL, not Dart loops.
- FEATURE-FIRST + CLEAN LAYERING (domain/data/presentation). Domain is pure (no Flutter, no I/O).
  Dependencies point inward only. UI never touches the DB directly.

THE NON-NEGOTIABLE INVARIANT
----------------------------
Every persisted entity has: id (UUID v4, client-generated) + createdAt + updatedAt + soft-delete flag.
This single rule is what keeps future cloud sync a drop-in instead of a painful migration.
NEVER persist an entity without it.


KNOWN PITFALLS / RISKY AREAS
----------------------------
- LOGGING FRICTION = DEATH. If logging a session ever takes more than a few seconds or many taps,
  retention collapses. Guard the quick-log path on every change. Optional context (feeling/equipment)
  must never block saving.
- EMPTY-APP PROBLEM. New users with no data see no trends -> no value -> churn. Onboarding and
  motivating empty states must create early wins. Never ship a blank dead-end screen.
- GAMIFICATION CAN BACKFIRE — AND IT'S NOW THE CORE, SO THIS IS THE #1 CRAFT RISK. Done wrong it feels
  gimmicky/naggy/dishonest and cheapens a serious improvement app. It must be EARNED, honest,
  meaningful, real-tennis-credible, occasional (no spam). See the North Star guardrails. "Lightweight"
  no longer means "minor" — it means restrained & tasteful while being central.
- SCOPE CREEP TOWARD COMMUNITY/CLUBS. Community is the planned future direction, which makes it tempting
  to build early. Architect community-ready (deterministic scoring, stable ids, owner seam); BUILD the
  single-player gamified loop first. Don't build leaderboards/friends/sharing yet.
- DESIGN DRIFT. Without discipline, one-off widgets/colors accumulate into visual chaos. The
  design_system/ module is the ONLY source of visual truth — extend it, don't bypass it.
- WIDE REBUILDS. Coarse Riverpod providers cause rebuild storms and jank. Keep providers granular.
- TRENDS IN DART. Aggregating full tables in Dart loops gets slow as history grows. Do aggregation
  in SQL (Drift).


UX INSIGHTS THAT MUST REMAIN
----------------------------
- The product IS the gamified loop: play -> fast log -> skills/XP/level/streaks/badges update -> see
  your game grow -> come back to level up. Every feature must feed the Player Profile / progression /
  motivation, or it is out of scope. (See North Star.)
- Priority order for all trade-offs: UX > clarity > maintainability > performance > technical elegance.
- The unique selling point is correlating PERFORMANCE with FEELING/MENTAL STATE + EQUIPMENT. Protect
  this connection in the data model and the insights UI; it is the reason to use tennisnow over a notes app.
- Feeling/mental-state data is personal. Treat it with care; never send it off-device or to analytics
  without explicit consent.
- Every screen must show real loading/empty/error/success states with immediate feedback. Optimistic
  UI for logging.


RECURRING MISTAKES TO AVOID
---------------------------
- Putting business logic in widgets, or calling the DB from the UI. Always go through a repository interface.
- Hard-coding colors/sizes/durations instead of using design_system tokens.
- Creating a one-off component when a reusable one fits — extend the reusable one.
- Using setState for app/business state instead of Riverpod.
- Persisting an entity without the id/createdAt/updatedAt/soft-delete invariant.
- Adding cloud/backend/club/event work "while we're here." It is out of v1 scope.

- Offline-first: the core loop must work with no network.
- Clean long-term foundation was explicitly prioritized over a throwaway MVP — invest in the domain

ESTABLISHED REUSABLE PATTERNS — GAMIFICATION (first built in features/gamification)
----------------------------------------------------------------------------------
- DERIVED-NOT-STORED: streaks and badges are COMPUTED from existing sessions — no new table, no
  migration. Same approach as progress. Prefer deriving over persisting until there's a real reason
  to store (e.g. "newly unlocked" toasts later would need a tiny persisted marker).
- STREAK LOGIC is a pure StreakCalculator.compute(dates, today) with an INJECTED clock (repository
  takes `now`) so it's deterministic and unit-tested. This is the date-window logic deferred earlier;
  it lives in Dart on purpose (consecutive-day runs aren't portable SQL). Grace rule: a streak stays
  alive if today OR yesterday is logged.
- COMBINING STREAMS: lib/core/utils/combineLatest2 merges two reactive sources (SQL aggregates +
  dates) without rxdart. Reuse it instead of adding a dependency or nesting StreamBuilders.
- BADGES: a small curated catalog (BadgeCatalog.all) of pure BadgeDefinitions; evaluate(inputs)
  returns Achievements (earned + progress). Add a badge = add a definition + an icon mapping in
  presentation (badgeIconFor). Keep the set small and meaningful (anti-gimmick rule).
- CROSS-FEATURE UI COMPOSITION is allowed via a feature's PUBLIC widget (Progress embeds
  gamification's GamificationStrip). Never import another feature's data/domain internals — see
  CLAUDE.md cross-feature rule.
- SUPPLEMENTARY WIDGET STATE EXCEPTION: a secondary widget on an already state-complete screen may
  render nothing while loading/on error (GamificationStrip uses maybeWhen→shrink) instead of a
  spinner. Only for non-critical, fast, local data — never for a screen's primary content.

SKILL CAPTURE (features/skills, ADR-008)
----------------------------------------
- Optional "Skills worked on" sheet on the log form: pick skills (grouped by SkillCategory) + rate each
  1-5. Persisted PER SESSION in the skill_ratings table (sync-ready cols). NEVER blocks Save (★/§4).
- PERSISTED, not derived: skill self-ratings are user input that can't be re-derived. The PER-SKILL
  SCORE (recency-weighted, current form) IS derived from them via SkillRatingCalculator (pure, injected
  now, half-life GameBalance.skillRecencyHalfLifeDays=30). Shown in Progress "Your skills" (SkillsSummary).
- DELETED-SESSION CORRECTNESS without cross-feature coupling: watchActiveSkillRatings() INNER JOINs
  sessions and filters both deletedAt null — ratings of a soft-deleted session drop out automatically,
  so session_logging never needs to know about skills.
- EDIT = REPLACE: replaceForSession soft-deletes a session's existing active ratings (tombstone) and
  inserts the new set in one transaction. Prefill on edit via ratingsForSession.
- CROSS-FEATURE WIRING: LogSessionController.save now returns the saved TennisSession (not bool) so the
  log SCREEN can then call skillRatingControllerProvider.save(session.id, playedAt, map). Presentation
  composing another feature's public provider is allowed; session_logging never imports skills internals.
- Table SkillRatings -> row SkillRating; domain entity is SkillSelfRating (avoid the generated-class
  clash, same trick as Sessions/TennisSession).
- SkillScore (the recency-weighted per-skill aggregate) lives in shared/domain/skill/ (NOT skills/domain)
  — it's part of the cross-cutting Skill Model (★B) and a 2nd feature (player_profile) reads it. Promoted
  the moment player_profile needed it (same rule as SessionType/AppDatabase). The CALCULATOR stays in
  skills/domain (it depends on SkillSelfRating, skills-owned).

PLAYER PROFILE / RADAR + SKILL-WORK XP (features/player_profile)
---------------------------------------------------------------

  ratable categories (strokes, shot quality, physical, mental) on top of the level/XP card. matchCraft &

  each category's rated skills (0 + hasData=false when none). Deterministic, tested, no Flutter/I-O — same
  shared-domain-scoring discipline as XpRules/StreakCalculator. overall() = mean of categories-with-data.
- RADAR is a dependency-free CustomPainter in design_system (SkillRadarChart + RadarEntry), like
  MiniLineChart. Reusable DS component, never a one-off (§5). Takes already-computed 0..1 entries; pure UI.
- LEVEL CARD reuse: extracted PlayerLevelCard (gamification public widget, takes a PlayerLevel) so the
  Progress strip AND the profile screen share ONE level visual — don't duplicate progression widgets.
- CROSS-FEATURE COMPOSITION ONLY: player_profile imports gamification's + skills' PUBLIC providers/widgets
  (gamificationProvider, skillScoresProvider, PlayerLevelCard, SkillsSummary) and shared/domain — never a
  feature's data/ or domain/ internals. This is the allowed pattern; keep it that way.
- ENTRY POINTS: the Progress level card is tappable -> /profile, and the "Your skills" header has a "View
  profile" button. Empty state SELLS the game (log + tag skills), with a CTA to /log.
- SKILL-WORK XP BONUS (★C, was the deferred TODO): XpRules.totalXp gained skillSessions (+GameBalance
  .xpPerSkillSession=5 each). Counts DISTINCT skill-tagged active sessions (watchSkillTaggedSessionCount:
  count(distinct sessionId) over the active inner-join) — PER SESSION not per rating, so it's honest and
  non-farmable. Default 0 keeps prior XP behavior. DriftGamificationRepository now combineLatest3 (added a
  3rd reactive source); combineLatest3 lives in core/utils next to combineLatest2.
- GAMIFIED "CHARACTER SHEET" REDESIGN (profile now reads like an RPG sheet, not a flat stats page):
  order is level+title hero (PlayerLevelCard) -> live streak (StreakBanner) -> radar -> categories ->
  next badge (NextBadgeCard) -> top skills. The hero is PRIMARY here (not supplementary): it shows a quiet
  skeleton while gamificationProvider loads (vs the Progress strip which shrinks); the badge band stays
  supplementary (shrink while loading).
- EDGE / WORK-ON-NEXT (honest, derived, NOT invented): PlayerProfileBuilder.strongest(cats) = highest
  category with data; .focus(cats) = an actionable next-step nudge — prefers a not-yet-started category
  (fills out the radar) else the weakest; null only when nothing is rated. Both pure + tested. UI shows the
  focus chip ONLY when it differs from the edge (no contradictory "edge X / work on X"). This is the
  gamified-but-honest pattern: surface guidance straight from the radar shape, never fabricate a target.
- NextBadgeCard = NEW reusable PUBLIC gamification widget (gamification/presentation/widgets): the closest
  unearned badge + AppProgressBar + earned count, tappable to /achievements; celebratory "all earned" state.
  Takes a GamificationSnapshot (public domain). Reuse it anywhere a "next trophy" nudge fits (§5), don't
  re-roll a one-off badge preview. Category bars + this card both use AppProgressBar (one progress visual).

FELT-MOMENTS — EARNED-PROGRESSION FEEDBACK AFTER SAVE (★/§4/§5)
--------------------------------------------------------------
- After logging, the player SEES what they earned (XP, level-up, new badge). Done with ONE tasteful,
  NON-BLOCKING SnackBar — celebratory & on-brand (primaryDark bg + accent medal) only on a real level-up
  or freshly unlocked badge; otherwise a quiet "+X XP" confirm. Never a blocking dialog, never spammy
  (guardrail: meaningful, not noisy). A negative XP delta (e.g. an edit removing a win) shows no "+XP".
- PURE DIFF: ProgressionDelta.between(before, after) (gamification/domain) — xpGained, level-up, NEWLY
  earned badges (set-diff of earned ids). before==null -> no gain/celebration (honest fallback). Tested.
- CROSS-FEATURE REWARD SEAM (important pattern): session_logging must NOT import gamification/domain.
  So the whole capture+diff+show is wrapped in a PUBLIC gamification presentation object, ProgressionReward
  (progressionRewardProvider): captureBaseline() on screen open, showEarned(messenger, isEdit) after the
  write. The log screen only holds this object (public surface) — snapshot types & delta stay inside
  gamification. Reuse this seam for any feature that needs felt rewards.
- DETERMINISTIC SNAPSHOTS: baseline + after are one-shot fresh reads via repo.watch().first (each runs a
  fresh aggregate query, so 'after' reflects the just-written rows). Baseline is captured in initState (no
  Save-tap latency); showEarned is called AFTER context.pop() and is safe because ProgressionReward depends
  only on the captured repo + app-level messenger, never on the disposed widget (no ref/context/mounted).

WEEKLY QUESTS (features/quests)
-------------------------------
- WHAT: a "This week's quests" card on the Progress tab = 3 small, optional, ACHIEVABLE weekly goals:
  (1) log 3 sessions, (2) work this week's ROTATING focus skill in 2 sessions, (3) note mood/energy in
  2 sessions. Deliberately inclusive — NO match requirement, so a training-only hobby player can complete
  every quest (achievable = motivating, not nagging; ★D/§4). Hits 3 pillars: streak/consistency, the skill
  model, and the human side.
- FULLY DERIVED-NOT-STORED: the board is a PURE function WeeklyQuests.boardFor(now, sessions, skillTags)
  (quests/domain) — no new Drift table, NO schema bump (stayed v4), injected clock, server-recomputable.
  Same catalog+pure-function discipline as BadgeCatalog/StreakCalculator. DON'T add a quests table unless
  something genuinely un-derivable appears (e.g. dismissed/seen state).
- NO SEPARATE QUEST XP (important honesty call): completing a quest grants ZERO extra XP. Doing the quest
  IS logging sessions/skills/feeling, which already grant XP via the normal path. Adding quest XP would
  double-count and invite farming + weekly-reset banking complexity. Quests CHANNEL the work that already
  levels you, they don't bolt on points. Revisit only with a deliberate, un-farmable design.
- ROTATING FOCUS SKILL: deterministic by week index = (weekStart - 2024-01-01 Monday).inDays ~/ 7, mod the
  curated focusSkillRotation list (stroke ids first). Fresh focus every Monday (fresh-start effect) with
  zero stored state. Quest id stays 'weekly_skill_focus' (stable, community-ready); only the skillId rotates.
- WEEK WINDOW: local Monday 00:00 (inclusive) .. next Monday 00:00 (exclusive). DateTime.weekday: Mon=1..Sun=7.
- DATA SEAM: DriftQuestRepository combineLatest2(watchActiveSessions, watchActiveSkillRatings) -> maps Drift
  rows to feature-neutral carriers (QuestSessionInput{id,playedAt,hasFeeling}, QuestSkillInput{sessionId,
  skillId}) -> pure evaluator. Domain never imports Drift rows or another feature's entity. Added a reactive
  watchActiveSessions() (full rows) next to allActiveSessionsOnce() — general-purpose, no schema change.
- FELT, NOT NOISY: progression is felt right on the card — goal-gradient AppProgressBar + an on-brand "done"
  state when complete. NO extra post-save SnackBar (the existing felt-moment already fires; a 2nd would be
  noise). New reusable design-system component: AppProgressBar (animated pill bar) — use it for any goal bar.

ESTABLISHED PATTERNS — PROGRESSION & SKILL FOUNDATION (gamification-ready, ADR-007)
----------------------------------------------------------------------------------
- SKILL MODEL: lib/shared/domain/skill/ — Skill, SkillCategory, SkillCatalog (canonical taxonomy, ONE
  source of truth like BadgeCatalog). Pure, Flutter-free. Skill.id is a STABLE, community-facing key —
  never change it once shipped. matchCraft & equipment are derived categories (not in the taggable
  catalog). Extending the model = add to SkillCatalog AND the CLAUDE.md ★ taxonomy.
- PROGRESSION SCORING is PURE + DETERMINISTIC (community-ready): lib/shared/domain/progression/
  xp_rules.dart (XpRules.totalXp from cumulative facts) + player_level.dart (PlayerLevel.forXp). All
  balancing numbers live in lib/core/constants/game_balance.dart (XP awards, level curve, titles) —
  NEVER scatter game constants. Re-derive level from XP; never store an opaque level.
- XP is from MONOTONIC cumulative facts (sessions, matches, wins) so it only ever goes up. Streak does
  NOT feed XP (would make XP fluctuate by day). Completeness/skill-work bonuses join later without
  breaking determinism. Level curve: step(L)=base100 + (L-1)*50.
- GAMIFICATION SNAPSHOT now carries the Player Profile seed: level (PlayerLevel) + streak + badges.
  Computed in DriftGamificationRepository from the SAME aggregates it already reads (no migration, no
  new persistence — derived-not-stored). The GamificationStrip shows a Level/XP card on top.
- WHY this matters: this is the gamification-ready foundation. New progression features build on these
  pure modules (testable, server-recomputable) — do NOT invent a parallel scoring system or put scoring
  in widgets.

PERSISTENCE SPLIT — TWO STORES, DIFFERENT JOBS (since onboarding, ADR-005)
--------------------------------------------------------------------------
- DRIFT (lib/shared/data/app_database.dart) = domain data that is sync-ready (sessions). Carries the
  id/createdAt/updatedAt/soft-delete invariant. Will sync to cloud one day.
- SHARED_PREFERENCES (lib/shared/data/app_preferences.dart, AppPreferences) = DEVICE-LOCAL UI prefs
  that must NEVER sync (onboarding-seen; later: theme). Decide store by this question: "should this
  follow the user to a new device?" Yes -> Drift. No -> AppPreferences.
- BOOTSTRAP: main() is async — ensureInitialized + load SharedPreferences, then inject via
  sharedPreferencesProvider.overrideWithValue in ProviderScope. The router reads prefs SYNCHRONOUSLY
  (that's why prefs load before first frame).

SETTINGS / DEVICE-LOCAL PERSONALIZATION (features/settings)
-----------------------------------------------------------
- Settings are device-local prefs (AppPreferences): displayName + defaultSessionType. Exposed

- The log form reads the default session type in initState via ref.read(settingsControllerProvider)

- SHARED DOMAIN GREW: SessionType moved from session_logging/domain to shared/domain because a 2nd

ONBOARDING / ROUTER GATE PATTERN
--------------------------------
- The router is a PROVIDER (goRouterProvider) so it can read prefs. A redirect gates first-launch:

- Onboarding is skippable and shown once; it exists to beat the empty-app problem — keep it short and

BACKUP / RESTORE (features/backup)
----------------------------------
- Local, offline, dependency-free: export = serialize active rows to a versioned JSON envelope
  ({app:'tennisnow', format:1, sessions:[], equipment:[]}) and COPY to clipboard; restore = paste +
  parse + upsert. No file plugins (clipboard is the universal cross-platform path that also works on
  the web build). File download/share is a future enhancement.
- Backup works at the PERSISTENCE (row) level on the shared AppDatabase, so it depends only on
  shared/ — never on a feature's domain/data mappers. Bump BackupService.formatVersion if the JSON
  shape changes.
- Restore is a MERGE by UUID (insertOnConflictUpdate) → idempotent, never deletes existing data.
- Privacy: a backup contains personal notes/feelings; only ever created on explicit user action and
  kept on-device/clipboard (CLAUDE.md §7). Warn the user to store it safely.

EQUIPMENT STRINGING + PERFORMANCE-BY-EQUIPMENT (extends equipment + progress)
-----------------------------------------------------------------------------
- Rackets carry optional stringing: stringName, tensionKg (REAL, kg), lastStrungAt. Shown/edited
  only when type==racket; cleared when type changes away. Tile shows "23 kg · String · strung Nd ago"
  with a gentle "time to restring?" hint after EquipmentTile.restringHintDays (60).
- copyWith can't null-out fields; EquipmentController.save builds the entity explicitly with the
  passed stringing values (so users can clear them).
- "Performance by equipment" = SQL GROUP BY sessions.equipment with AVG(performance), filtered to
  rows that have equipment+performance, ordered by avg desc (watchPerformanceByEquipment). Carrier
  EquipmentPerformanceRow (shared/data) -> domain EquipmentPerformance (progress). It groups by the
  denormalized session.equipment NAME — so per-historical-stringing analytics would need snapshotting
  the stringing onto the session (postponed; would also want the equipmentId FK).

DB MIGRATIONS — MANDATORY ON ANY SCHEMA CHANGE (since equipment, ADR-006)
-------------------------------------------------------------------------
- There is real on-device data (incl. web testers). NEVER drop/recreate. Bump AppDatabase
  schemaVersion and add an additive onUpgrade step (MigrationStrategy). v1->v2 created equipment_items;
  v2->v3 added stringing columns via m.addColumn (nullable columns only).
- Pattern: onCreate: (m) => m.createAll(); onUpgrade: if (from < N) ...createTable/addColumn...;
- Table-vs-entity naming (avoid the generated-class clash): table EquipmentItems -> row EquipmentItem,
  domain entity Equipment (same trick as Sessions/Session vs TennisSession).
- Equipment on a session is stored DENORMALIZED as the name string in sessions.equipment (no sessions
  migration, log flow unchanged). A future equipmentId FK is the clean upgrade when building
  equipment-vs-performance analytics; until then, correlation can group by name.

DRIFT GOTCHAS (learned)
-----------------------
- Default SQL column names are snake_case of the Dart getter (playedAt -> played_at). Prefer the
  type-safe expression API (sessions.performance.avg(), .count(filter: ...)) over raw SQL strings to
  stay refactor-safe.
- Storing DateTime: Drift stores it as a Unix timestamp; avoid hand-rolled epoch comparisons in raw
  SQL. "This week"/streak windows were intentionally deferred to the gamification feature to dodge
  this coupling. Revisit deliberately when building streaks.
- WEB needs the sqlite3 WASM runtime: drift has no native SQLite in the browser, so `sqlite3.wasm` +
  `drift_worker.js` MUST sit in web/ (served from the root). `flutter create` does NOT provide them,
  so the CI `pages` workflow curls them in before `flutter build web` (forwards-compatible with the
  drift ^2.18 in pubspec; URLs are the simolus3 drift/sqlite3.dart GitHub releases). `_openConnection`
  passes the URIs explicitly via DriftWebOptions so web never silently falls back to a broken DB. If
  the web app "loads but can't save/load sessions", suspect these assets first.
- WEB renderer = WasmGC: the `pages` workflow builds `flutter build web --wasm` (skwasm). Flutter emits
  a JS fallback (dart2js/CanvasKit) automatically, so WasmGC-less browsers still run — no one is locked
  out. Runs SINGLE-THREADED on GitHub Pages on purpose: multi-thread skwasm needs cross-origin isolation
  (COOP/COEP), which GitHub Pages can't set natively (would need the coi-serviceworker hack) AND which
  currently triggers a Chrome blank-screen bug (flutter#184843). Do NOT add COOP/COEP headers here until
  that bug is closed AND a header path exists — single-threaded WasmGC is already the faster, safe win
  over plain dart2js. The drift sqlite3.wasm/worker assets are independent of the Flutter renderer wasm;
  no conflict. Requires Flutter >= 3.27 (withValues; we run 3.44.1).
- CI = TWO workflows: `ci.yml` (analyze + flutter test on push/PR) and `pages.yml` (build+deploy,
  main only). ci.yml runs build_runner FIRST (analyzer/tests import drift *.g.dart). The analyze gate is
  `dart analyze --format=machine` piped to grep that fails ONLY on `^(ERROR|WARNING)\|` lines. Why the
  song-and-dance (burned ~3 CI rounds learning this): BOTH `flutter analyze` AND bare `dart analyze` exit
  non-zero on info-level issues in this project (dart analyze exited 3 on 88 infos), so neither exit code
  nor `--no-fatal-infos` gives an "errors-only" gate. Machine format (uppercase SEVERITY first field, no
  color/bullets) is the only deterministic way to isolate severity. So: ERRORS (incl. unused_import /
  unused_local_variable, promoted to error in analysis_options) + WARNINGS gate; the ~88 auto-fixable style
  infos (prefer_const, require_trailing_commas, prefer_null_aware) stay advisory. Clear them with
  `dart fix --apply` in a Flutter-equipped session (can't run here — Flutter not installed), then tighten to
  a bare `dart analyze --fatal-infos`. Lesson: the un-gated Replicate asset commits shipped 3 real dead
  imports — ci.yml caught all three. Don't merge analyzer ERRORS. ALSO: when reading failed CI logs, the
  error lines are at the TOP of analyze output (file order) — `tail` hides them; fetch enough lines.

BACKUP/EXPORT MUST COVER EVERY TABLE + COLUMN (learned the hard way)
-------------------------------------------------------------------
- BackupService (features/backup) hand-maps each row <-> JSON. It is NOT reflection-based, so adding a
  table or a column is silently NOT backed up until you extend it. When you touch the schema, also
  update BackupService: add the column to the *toJson/*fromJson pair, or add a new top-level array +
  its allActive<X>Once()/upsert<X>() pair on AppDatabase (mirror sessions/equipment exactly).
- Real bug fixed once: equipment stringing (stringName/tensionKg/lastStrungAt) and the ENTIRE
  skill_ratings table were missing from export/import -> restore wiped them. Now covered; envelope
  bumped to format v2. Keep import tolerant of older envelopes (missing arrays -> empty, missing
  nullable fields -> null) so v1 backups still restore. No schema bump needed for backup-only reads.

PLANNED FEATURE: TRAINER MODE (Coach Mode)

STATUS: Not yet built. Architect for it now; build after the single-player gamified loop is solid.

CORE DECISION: Local-first to start, cloud-ready from day one.

WHAT TRAINER MODE IS:

      rating(1–5), notes?, assessedAt, createdAt, updatedAt, deletedAt }
  All studentId FKs are stable UUIDs — the cloud-sync / RLS seam is already there.

NAVIGATION:

  own self-ratings. Future: merge/compare trainer vs. self-assessment.

KI SUPPORT FOR TRAINERS (AI-first, cost-aware per §11):
  - Input: last N training notes for a student + skill assessments + goals (pre-aggregated in domain,

  - Output: development pattern analysis, recommended training focus, exercise suggestions, mental tips,

AVATAR SYSTEM — BUILT (Gamification 2.0, DiceBear adventurer)
=============================================================
STATUS: BUILT (v1). DiceBear adventurer SVG avatars on the Player Profile, with a live editor.
  The custom layered-PNG plan below it (struck through) was TRIED and ABANDONED — read why first.

WHY THE LAYERED-PNG / REPLICATE PLAN WAS DROPPED (key learning):
  We ran a real POC (committed under assets/images/avatar_poc/, generator /tmp/avatar_layer_poc.py):
  generate each body part as an isolated PNG via Replicate flux-schnell, strip the white background
  with Pillow, alpha-composite the layers in Dart. RESULT: it does NOT work. flux-schnell gives no
  control over scale/anchor/proportion across separate prompts, so the hair layer doesn't sit on the
  head, eyes/mouth float, etc. The "PITFALL — LAYER ALIGNMENT" warning turned out to be fatal, not
  manageable. Full PRESET characters (one prompt → whole figure) look great, but lose the deep
  customization the user wanted. So a generative-per-layer pipeline is the wrong tool here.

THE SOLUTION — DiceBear adventurer (decided & built):
  DiceBear (https://www.dicebear.com, MIT, API v9.x) ships avatar styles whose layers are DESIGNED to
  compose perfectly — alignment is solved by the library, not by us. The `adventurer` style is a
  friendly flat-vector character that fits the brand. We render it at RUNTIME as an SVG from the public
  HTTP API; the params ARE the avatar (deterministic URL), so nothing is generated or stored as images.
  - NO Replicate, NO Pillow, NO committed avatar PNGs, NO build step for avatars.
  - Render via flutter_svg `SvgPicture.network(config.svgUrl)`. URL is built by AvatarConfig.svgUrl.
  - Endpoint: https://api.dicebear.com/9.x/adventurer/svg?skinColor=..&hair=..&hairColor=..&eyes=..&
    mouth=..&backgroundColor=..&backgroundType=solid&radius=50  (radius=50 → pre-clipped circle).
  - NETWORK NOTE: api.dicebear.com is NOT in the on-web session's network allowlist (returns 403 in
    this dev env), so the avatar can't be live-previewed from inside a web session — that's an env
    policy limit, not a code bug. On real devices the app reaches it fine. If avatars render as the
    grey person-placeholder in a web session, suspect the allowlist first. (Self-hosting DiceBear or
    bundling its sprites locally is the offline-first upgrade path if we ever want zero network — the
    package `@dicebear/collection` is MIT; could pre-render the catalog to assets. Postponed.)

ADVENTURER PARAM VALIDITY (PITFALL — learned): the adventurer style only accepts hair = `short01`..
  `short19` and `long01`..`long26`. Made-up ids like `curly01`/`braids01`/`pixie` are SILENTLY ignored
  (DiceBear falls back to a default) — no error, just "my hair picker does nothing." eyes = `variant01`
  ..`variant26`, mouth = `variant01`..`variant30`. skinColor/hairColor/backgroundColor accept ANY hex
  (6 chars, no '#'). Whenever extending AvatarCatalog, only use ids in these ranges.

WHAT'S BUILT (files):
  - shared/domain/avatar/avatar_config.dart — AvatarConfig value object (skinColor, hairStyle,
    hairColor, eyeStyle, mouthStyle, bgColor), immutable + copyWith, toJson/fromJson + svgUrl getter.
    Pure domain (no Flutter). defaultConfig gives every new player a valid avatar instantly.
  - shared/domain/avatar/avatar_catalog.dart — AvatarCatalog: pure catalog of AvatarOption lists
    (skinColors, hairStyles, hairColors, eyeStyles, mouthStyles, bgColors). Single source of truth,
    same pattern as BadgeCatalog/SkillCatalog. Extend deliberately; respect the param ranges above.
  - design_system/widgets/avatar_widget.dart — AvatarWidget(config, size): renders the SVG with a

  - features/player_profile/presentation/providers/avatar_provider.dart — avatarConfigProvider

================================================================================
CLOUD PIVOT: SUPABASE BACKEND + AUTH + TIERS  (greenlit 2026; build in progress)
================================================================================
STATUS: Decided and being built. This supersedes the original "local-only, no backend yet" stance.
Supabase itself gets configured AFTER the code is made cloud-ready (this section is the plan; the
backend wiring comes next). The app is NOT live yet → there is NO existing user data to migrate, so we
can change schemas/persistence freely WITHOUT migration headaches right now (decided: migration of
pre-existing local data is a non-issue at this stage).

THE GOAL (in one sentence):
  Every input, setting and bit of progression for a signed-in Pro user lives in Supabase, so signing in
  on ANY device restores the exact same state — nothing lost, nothing overwritten, nothing reset.

------------------------------------------------------------------
A. THE THREE USAGE TIERS (this shapes the WHOLE persistence design)
------------------------------------------------------------------
There are now THREE modes the app can run in. Persistence behaves differently in each:

  1. DEMO MODE (no login):
     - The app is fully usable to try out, BUT NOTHING IS PERSISTED. Ephemeral only.
     - Implementation: an in-memory / no-op repository set (data lives only for the session, gone on
       app close). No Drift writes, no Supabase. A clear, non-nagging "you're in demo — sign in to keep
       your progress" hint where it helps (never blocking the try-it loop).
     - Purpose: let a new user feel the core loop instantly (beats the empty-app problem) without a
       signup wall, but make it honest that nothing is saved.

  2. FREE MODE (signed in, not paying):
     - The app can be used only MINIMALLY (a limited subset of features — exact limits TBD, see open
       questions), AND persistence is LOCAL-ONLY (Drift on-device). NO CLOUD SYNC for free users.
     - So a free user keeps their data on THIS device, but it does NOT follow them to another device.
     - Implementation: the Drift repositories (today's local stack) with the cloud-sync layer DISABLED.

  3. PRO MODE (signed in, paid subscription):
     - FULL feature set + CLOUD SYNC. Everything (sessions, skills, equipment, settings, avatar,
       unlocks, trainer data, …) is stored in Supabase and synced across devices.
     - Offline-first preserved: Drift remains the on-device cache; writes go local-first then sync up;
       sign-in on a new device pulls the full state down.

  DESIGN CONSEQUENCE: persistence must be SWAPPABLE BY TIER behind the existing repository interfaces.
  A single `AppMode { demo, free, pro }` (derived from auth state + entitlement) selects which
  repository implementations are provided (Riverpod override at the root). UI code NEVER branches on
  tier for storage — it always talks to the same repository interface; only the bound implementation
  changes. This is exactly why we kept persistence behind interfaces from day one.

  Tier gating of FEATURES (not storage) is separate: a small `entitlementProvider` exposes the current
  tier so UI can show upgrade prompts / lock Pro features. Keep paywall logic in ONE place (an
  entitlement/feature-gate module), never scattered `if (isPro)` checks in widgets.

------------------------------------------------------------------
B. AUTHENTICATION (Supabase Auth)
------------------------------------------------------------------
  - METHODS: (1) Email MAGIC LINK (passwordless — primary), (2) GOOGLE sign-in (OAuth). No
    email+password flow (decided — avoids password reset/support/attack surface).
  - Supabase Auth provides the session + a stable `auth.uid()` → this IS the `userId` the whole schema
    keys on. Fill the long-planned owner seam with this id.
  - A new `features/auth` feature owns: sign-in screen (magic link entry + "Continue with Google"),
    auth state provider, session handling, sign-out. Lives behind an `AuthRepository` interface
    (SupabaseAuthRepository impl) so it's testable and swappable.
  - ROUTER GATE extends the existing onboarding gate: routes are gated by AppMode. Demo users can roam
    the app; certain actions ("keep your progress", Pro features) route to /auth or an upgrade sheet.
    Reuse the goRouterProvider + redirect pattern already used for onboarding — do NOT bolt on a second
    gating mechanism.
  - Magic-link deep linking: the email link must reopen the app (mobile deep link / universal link;
    web redirect). This needs platform config (iOS associated domains, Android intent filters) + a
    redirect URL allowlisted in Supabase. Note for setup phase.
  - SENSITIVE DATA (§7): feeling/mood/notes are personal. With cloud sync they now LEAVE the device →
    this is exactly the "explicit user action / consent" boundary the privacy rule warned about.
    Signing into Pro IS that consent, but: keep RLS strict, never log personal fields, and keep the
    store privacy declarations accurate (data now leaves the phone for Pro users).

------------------------------------------------------------------
C. OFFLINE-FIRST SYNC ARCHITECTURE (Pro mode)
------------------------------------------------------------------
  - PATTERN: local-first write-through. UI → repository → Drift (immediate, optimistic) → sync engine
    pushes to Supabase when online; pulls remote changes into Drift. The UI keeps reading Drift streams
    (today's reactive pattern is unchanged), so the fast-log path stays sacred and offline still works.
  - WHY this and not "talk to Supabase directly": direct cloud reads/writes would reintroduce logging
    friction (the #1 risk) and break offline. The cache-then-sync model keeps logging instant.
  - CONFLICT RESOLUTION: every entity already has updatedAt + UUID id + soft-delete. Use last-write-wins
    by updatedAt per row (good enough for a single-user-multi-device app; there's no concurrent
    multi-user editing of the same row). Soft-delete tombstones replicate so deletes propagate (don't
    hard-delete — a hard delete can't sync as a deletion).
  - The SYNC ENGINE is its own module (shared/data/sync or a dedicated service). Options to evaluate at
    build time: (a) hand-rolled push/pull over the Supabase client using updatedAt watermarks per table,
    (b) Supabase Realtime for live pull, (c) an existing Drift<->Postgres sync helper if one fits. Lean
    toward the simplest correct option first (watermark push/pull); add Realtime only if live
    multi-device updates are needed.
  - DERIVED-NOT-STORED STILL WINS: streaks, XP, levels, badges, quests, skill scores, profile radar are
    all PURE functions over the synced raw rows. So we sync the FACTS (sessions, skill_ratings,
    equipment, settings) and RE-DERIVE progression on each device identically — incl. cosmetic
    unlocks, which are a pure function of level. Do NOT sync
    derived numbers as authoritative — re-derive them. (A Supabase edge function can recompute the same
    values for server-side verification / future leaderboards — community-ready invariant pays off.)

------------------------------------------------------------------
D. WHAT EVERY PIECE OF STATE MAPS TO (the "store everything" requirement)
------------------------------------------------------------------
  ALREADY DRIFT TABLES → become Supabase tables (1:1, same columns + a `user_id` column, RLS on
  user_id):
    sessions, equipment_items, skill_ratings  (+ the planned trainer tables). NOTE: cosmetic avatar
    unlocks are DERIVED from player level (which is derived from synced sessions) — there is no
    unlocked_items table to sync. Syncing the sessions re-derives every unlock identically per device.
  Each Postgres table: same UUID PK, createdAt/updatedAt/deletedAt, plus user_id uuid references
  auth.users. RLS policy: a user can only see/write rows where user_id = auth.uid().

  TODAY'S DEVICE-LOCAL PREFS (AppPreferences / shared_preferences) → SPLIT by "should this follow the
  user across devices?":
    - SYNC TO CLOUD (belongs to the account): displayName, defaultSessionType, avatar config,
      onboarding-as-product-state if we want it cross-device, any personalization. These move into a
      `profiles` table (one row per user) OR a `user_settings` table. They are USER data now, not just
      device UI state.
    - STAY DEVICE-LOCAL (never sync): things that are genuinely per-device (e.g. "this device finished
      onboarding", theme if device-specific, the cached auth session). Keep these in shared_preferences.
    - The old rule ("Yes→Drift, No→AppPreferences") gets a THIRD bucket now: account-level settings →
      Supabase profiles. Re-evaluate each existing pref against: device-local vs account-level.

  AVATAR CONFIG: previously planned for AppPreferences (device-local). REVISIT: for Pro it must sync →
    store AvatarConfig in the `profiles`/`user_settings` row so the avatar follows the user. For
    free/demo it stays local/ephemeral. (Update the Avatar section's persistence note accordingly when
    building.)

  UNLOCKS (unlocked_items): cloud table for Pro (cosmetic unlocks follow the user), local for free.

  RESULT: for a Pro user, sessions + equipment + skills + settings + profile/avatar + unlocks + trainer
  data ALL live in Supabase under their user_id. Sign in on a new device → pull all of it → identical
  state. Nothing is overwritten or reset (we PULL then reconcile by updatedAt, never blindly wipe).

F. HOSTING & PAYMENTS (open, decide at setup time)
------------------------------------------------------------------
  - The MOBILE app ships via App Store / Play Store — it is NOT "hosted". "Hosting" applies to: a
    marketing/landing site, an optional Flutter WEB build, and any server-side functions.
  - SUPABASE covers auth, Postgres, RLS, storage, and edge functions (server-side logic / score
    verification / payment webhooks). That is the backend.
  - VERCEL (user suggested) is a fine host for a landing page or a Flutter-web build, but is NOT
    required for the backend (Supabase is). Alternatives for a web/static host: Cloudflare Pages,
    Netlify, Firebase Hosting — all comparable; pick by preference. NO strong reason to add Vercel
    unless/until there's a web frontend or marketing site to host. Don't add it speculatively.
  - PRO PAYMENTS (paid tier) — OPEN QUESTION, decide before building the paywall: on iOS/Android, Apple
    & Google generally REQUIRE their in-app purchase / subscription billing for digital goods (a Stripe
    web checkout for app subscriptions can get rejected). Practical path: native IAP via a layer like
    RevenueCat (handles iOS+Android subscriptions + entitlements) feeding the entitlementProvider;
    Stripe only for a pure web version. This is a deliberate decision for when monetization is built —
    not now.
